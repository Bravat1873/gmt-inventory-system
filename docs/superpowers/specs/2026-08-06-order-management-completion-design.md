# 订单管理字段补全设计

## 目标

将订单新增、修改和列表扩展为可保存的完整业务订单，而不是只保存客户和价格明细；所有变更均可追溯当前登录用户。

## 订单字段

订单主表新增并保存：订单日期、订单类型、订单状态、销售员、客户联系人、客户电话、订单备注、收货地址、收货联系人、收货联系电话、发货方式。订单编号继续由服务端生成；销售员在新建时默认当前登录用户，但允许修改。

## 订单明细

每条明细保存固定行号、SKU、订单数量和含税单价。界面通过物料编号选择 SKU，并只读显示物料名称、规格型号和单位。已发货数量由服务端根据发货记录累计；剩余数量始终由 `订单数量 - 已发货数量` 计算，前端不得手工编辑。

## 固定序号与排序

订单列表返回服务端计算的固定序号，顺序为 `created_at ASC, id ASC`。前端任意列排序只改变展示顺序，不重新计算该序号。明细行号在创建时按 10000 递增并持久化，编辑排序也不会改变。

## 数据迁移与接口

新增数据库迁移为销售订单补全字段、历史默认值及必要索引。创建与更新接口复用一个完整请求模型；更新时使用版本号保持并发保护。订单查询返回主表补全字段、固定序号以及已发货/剩余数量。

## 校验与错误处理

订单日期、类型、状态、客户、销售员、至少一条明细、正数订单数量和非负含税单价为必填或有效值。发货数量不得大于订单数量；SKU 不存在、乐观锁冲突或非法状态会返回清晰错误，且不会写入半条订单。

## 验证

覆盖创建、修改、SKU 回填、固定序号、已发货及剩余数量计算的后端测试；构建前端并启动前后端，使用登录会话验证订单列表和保存接口。
