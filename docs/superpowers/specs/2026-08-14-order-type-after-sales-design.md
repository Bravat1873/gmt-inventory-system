# 订单类型与售后联动设计

## 目标

将订单类型统一为固定三选一，并在订单管理、售后管理和新增/修改售后中清晰展示原订单类型。

## 订单类型规则

订单类型只能是：

- 工程订单
- 零售订单
- 前置订单

新增订单不自动选择默认值，用户必须明确选择。修改订单时如果历史订单类型为空或无法识别，也必须重新选择。前端使用下拉选择，后端对新增和修改请求执行同样的白名单校验，拒绝空值和其他值。

订单管理列表在客户列之后增加“订单类型”列，并支持排序。升序业务顺序为工程订单、零售订单、前置订单，降序反向；未知历史值始终排在三种有效类型之后。

## 历史数据迁移

新增数据库迁移统一已知旧值：

- `PROJECT`、`工程订单` 转换为 `工程订单`。
- `RETAIL`、`Sales`、`销售`、`零售订单` 转换为 `零售订单`。
- `前置订单` 保持不变。
- 空值和无法识别的旧值保持原样，不自动猜测。

迁移不得删除订单或修改订单状态、金额、客户、明细等其他字段。

## 售后联动

订单类型归属于原销售订单，售后单不重复保存订单类型。所有售后场景通过 `sales_order_id` 关联实时读取原订单类型：

- 售后管理列表在客户列之后增加“订单类型”列，并支持与订单管理相同的业务顺序排序。
- 新增售后的原订单搜索结果显示“订单号 / 客户 / 订单类型”。
- 选择原订单后，在售后基础信息区域显示只读“订单类型”。
- 修改和查看售后时显示关联订单当前的订单类型，不允许在售后页面修改。

如果历史订单类型为空或无法识别，售后页面显示“未设置”，但不阻止查看已有售后；新建售后仍可关联该订单，订单类型只读显示“未设置”。订单类型的修正必须回到订单管理完成。

## 接口与查询

- 订单列表与订单详情继续使用现有 `orderType` 字段，但值统一为中文业务值。
- 售后订单候选接口增加 `orderType`。
- 售后详情接口增加关联订单的 `orderType`。
- 售后列表查询增加 `orderType`，来源为关联的 `sales_order.order_type`。
- 后端排序白名单为订单和售后模块增加 `orderType`，使用相同业务顺序表达式。

## 验证

- 前端测试验证订单类型只能三选一、无默认选择、无效值无法提交。
- 后端测试验证空值和白名单外值被拒绝，三个有效值可新增和修改。
- 迁移测试验证已知旧值转换、未知值和空值保留。
- 订单列表测试验证订单类型展示与业务排序。
- 售后候选、详情和列表测试验证正确返回关联订单类型。
- 售后表单测试验证选择订单后只读显示类型且不能修改。
- 完整运行前后端测试、前端生产构建和 Docker 部署验证。

## 非目标

- 不允许自定义第四种订单类型。
- 不在售后表中冗余保存订单类型。
- 不允许售后页面修改原订单类型。
