# 三角色只读财务权限设计

## 目标

系统维持单角色模型，仅使用 `ADMIN`、`FINANCE`、`USER` 三种角色。所有已登录用户仍可查看各业务模块的数据；管理员保留全部操作权限。财务和普通用户均不能新增或修改用户信息，财务管理页面对财务用户仅提供查看入口，不允许登记款项、维护发票或复核。

## 角色规则

| 角色 | 用户管理 | 财务管理 | 其他模块 |
| --- | --- | --- | --- |
| `ADMIN` | 新增、修改、查看 | 全部操作 | 维持全部操作 |
| `FINANCE` | 仅查看 | 仅“查看” | 维持当前允许的操作，产品价格编辑仍允许 |
| `USER` | 仅查看 | 仅“查看” | 维持当前允许的操作 |

财务用户打开财务管理时，列表行只显示“查看”。“登记”“发票”“复核”等按钮均不渲染；即使直接调用相关接口，后端也返回无权限错误。管理员在财务管理中继续拥有原有全部操作。

## 实现边界

1. 在 `UserRole` 中定义清晰的能力方法：仅管理员可管理用户及写入财务；财务和普通用户在财务管理中只读。
2. 后端为用户新增、用户修改、资金登记、发票新增/删除、资金复核及发票复核增加角色校验。查询接口保持所有登录用户可访问。
3. 前端将当前用户角色传入列表页面，在用户模块隐藏财务与普通用户的新增/修改入口；在财务模块中仅向财务用户显示“查看”。对对话框打开方法增加同样的防护。
4. 不新增角色，不更改 `sys_user` 数据，不修改业务单据或发票数据，不新增数据库迁移。

## 错误和兼容性

后端拒绝操作时返回 HTTP 403 与“无此操作权限”。现有管理员操作流程和已有 API 路径不改变。现有前端测试补充角色可见性断言；后端测试补充财务用户禁止用户写入、财务用户禁止财务写入与管理员允许的断言。

## 验证

执行后端权限测试及受影响前端组件测试，再运行前端构建和后端测试。使用本地 Docker 重建服务，不执行会改动业务数据的 SQL。
