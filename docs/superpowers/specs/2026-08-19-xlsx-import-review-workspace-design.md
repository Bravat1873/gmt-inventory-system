# XLSX Import Review Workspace Design

## Goal

Replace the inconsistent XLSX import previews with one required review workflow for customer, supplier, product, and sales-order imports. Users can drag a workbook into the page, resolve every conflict row, edit imported data where necessary, and only then submit the batch.

## Scope

The import panel remains the entry point. The work includes the four import types `CUSTOMER`, `SUPPLIER`, `PRODUCT`, and `ORDER`, their preview/commit API contracts, and product-import deployment prerequisites.

It does not create or alter the supplier named Shenzhen Jimendi; that supplier will be maintained by the user.

## Review Workflow

1. The panel opens in a file-drop state. It accepts a dropped workbook or a file selected through the file picker, shows the permitted extension, the selected filename, and a download-template link.
2. Uploading always creates a preview batch. No customer import may auto-commit.
3. The review header shows total, valid, error, conflict, resolved, and unresolved counts. Filters expose All, Conflicts, Errors, and Resolved rows.
4. Errors prevent submission. Every conflict requires an explicit decision before submission.
5. The user can replace the file before submitting; the new preview resets all local decisions.
6. The commit button states the applicable operation and remains disabled with a direct reason while errors or unresolved conflicts remain.

## Conflict Model

The backend supplies normalized metadata for each conflict: the field/key label, a stable conflict group, the existing-record identifier and field snapshot where a persisted record is involved, and the imported row data. UI-only metadata is excluded from persisted business fields.

Each conflicting row exposes three choices:

- **Keep existing**: do not modify the matching persisted record. For product workbook duplicates, do not select that upload row for replacement.
- **Use imported**: persist this imported row. It overwrites the matching record for customers and suppliers; it creates/replaces the selected upload row for products; it replaces the matching order according to the defined order conflict policy.
- **Edit then use imported**: open row editing for user-editable import fields, revalidate and persist the revised staged row, then resolve it as Use imported.

The review table visually distinguishes conflicts, validation errors, skipped/kept rows, and resolved rows. The conflict detail exposes existing and imported values side by side for persisted-record conflicts. Product workbook duplicate rows compare the competing uploaded rows side by side.

## Import-Type Rules

### Customers

- Conflict key: normalized `customerName` against existing customers.
- A no-conflict workbook still remains in preview until the user submits it.
- Keep existing skips the row. Use imported updates the named customer. Edit then use imported updates the revised staged row.

### Suppliers

- Conflict key: normalized `supplierName` against existing suppliers.
- The existing overwrite and replace-all modes remain available. Conflict choices decide each same-name row; replace-all still disables active suppliers absent from the workbook only after user confirmation.
- Keep existing skips the matching row. Use imported updates it. Edit then use imported updates the revised staged row.

### Products

- Product import remains an administrator-only `PRODUCT_REPLACE_ALL` operation.
- Conflict key: `productCode + customerPartNumber`, detected only among valid rows in the uploaded workbook. Existing database products are not candidates because a successful commit deletes and rebuilds product data.
- A duplicate group must select zero or one uploaded row. Keeping a row selects it for the replacement; choosing another row selects that row instead; editing a row requires revalidation and recalculation of generated product code and unique identity before selection.
- The destructive-operation confirmation remains immediately before commit and accurately lists dependent data deleted by product replacement.

### Sales Orders

- Conflict key: Excel template field `externalOrderNo` (Chinese header: `外部订单号`) against `sales_order.external_order_no`.
- Internal system order numbers are generated by the system and are not accepted from the workbook.
- A conflicting existing order must not be silently skipped or mixed into a partial order commit. Keep existing skips the entire external-order group. Use imported replaces the entire matching order as one transaction; Edit then use imported updates the staged group and repeats validation before replacement.
- Rows of one external order continue to require consistent order-level fields and all lines must validate before that group can be submitted.

## Backend Contract and Data Integrity

- Replace stringly typed generic conflict decisions with explicit action values that represent keep, use-imported, and edit/use-imported resolution. Manual editing is represented by a staged-row update followed by use-imported.
- Validate that decisions belong to the batch, cover every conflict group as required, and are compatible with the import type. The server remains authoritative even if a client bypasses disabled UI.
- Preserve existing customer bank fields (`bankName`, `bankAccount`) during staged edits and commits.
- After a staged edit, rerun the same type-specific validation and conflict detection. Product edits additionally recalculate code-rule metadata and the composite unique ID.
- Ensure order preview conflicts are returned as conflicts rather than generic errors, and implement atomic group replacement only when the explicit use-imported decision is supplied.

## Product Import Prerequisites

- The deployment compose configuration must set `PRODUCT_REPLACE_IMPORT_ENABLED=true` for the backend; the `app.import.product-replace-enabled` setting continues to map from that environment variable.
- Add an idempotent Flyway migration which creates an enabled default warehouse only when no default warehouse exists. It must not create a second default warehouse or change an existing default warehouse.
- The product commit retains its existing checks for code rules, a default warehouse, valid supplier references, and administrator role.

## Frontend Structure

Split the oversized import panel into a container that owns file/preview/commit state and focused presentational components for:

- file drop zone and template link;
- review summary and filters;
- generic row conflict comparison and resolution controls;
- staged-row editing form;
- product duplicate-group review;
- sales-order group review.

Use the existing Vue, TypeScript, and CSS patterns. Preserve current API names where practical, but upgrade typed request/response contracts when required by the unified resolution model.

## Testing and Verification

- Frontend tests cover drag/drop upload, required preview for every type, summary/filter state, disabled commit rules, all three conflict choices, and staged edits.
- Backend tests cover each conflict key, decision validation, customer bank-field preservation, product internal duplicate selection and edited identity recalculation, order external-order conflict detection and atomic replacement, and default-warehouse migration behavior.
- Run the relevant frontend Vitest suites, backend Maven tests, and frontend production build. Verify the deployed compose configuration exposes the product replacement feature only through the explicit environment flag.
