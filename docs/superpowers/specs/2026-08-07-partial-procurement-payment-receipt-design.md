# 采购分批付款与分批收货设计

## 目标

采购付款和采购收货改为两条互相独立的进度线。采购单允许多次付款，也允许供应商分批发货后由用户按采购明细手工登记本次实收数量。付款是否结清不限制收货，货物是否收齐也不限制付款。

## 数据与状态模型

- `supplier_payment` 保留每次付款流水；取消一张采购单只能有一笔付款的约束。
- `goods_receipt` 和 `goods_receipt_item` 保留每次收货及各明细的实收数量。
- `purchase_order_item.received_quantity` 表示该明细累计实收数量，由每次有效收货累加。
- 已付金额由付款流水汇总，未付金额为采购总额减已付金额。
- 已收数量由采购明细累计实收汇总，未收数量为采购数量减累计实收数量。
- 对外同时提供付款进度和收货进度。采购总体状态由两条进度推导：两者都完成时为“已完成”；否则展示各自的待处理或部分完成状态，不以其中一条进度阻塞另一条。

## 付款流程

登记付款时锁定采购单并汇总既有付款。单次付款金额必须大于零，累计付款不得超过采购总额。保存新的付款流水后重新计算已付和未付金额；未结清时仍保留“登记付款”入口，结清后关闭该入口。

付款方式、备注、发票号和发票日期继续保存在每笔付款流水上。付款不改变收货资格，也不将采购单强制推进到只能收货的单一状态。

## 收货流程

登记收货弹窗展示采购单全部明细，包括采购数量、累计已收、本次实收和剩余数量。用户逐项填写本次实收数量，未到货项可填零，但一次提交至少有一项大于零。

服务端锁定采购单及相关采购明细，逐项校验本次实收为非负整数，并保证累计实收不超过采购数量。一次提交生成一张 `goods_receipt`，仅为本次实收大于零的采购明细生成收货明细。

每条有效收货明细同步增加采购明细累计实收数量，将对应数量从在途库存转入实际库存，并记录采购入库库存流水。未收齐明细保留剩余数量，后续可继续登记收货。全部明细收齐后关闭“登记收货”入口。

## 接口与界面

- 付款接口继续接收单次付款金额，并允许对尚未结清的采购单重复调用。
- 收货接口改为接收明细数组，每项包含采购明细 ID 和本次实收数量。
- 采购查询返回每条明细的采购数量、累计已收和剩余数量，并返回采购单级的已付、未付、付款状态、已收、未收和收货状态。
- 采购列表显示付款与收货的独立进度；未付清时显示“登记付款”，未收齐时显示“登记收货”。两个按钮可同时出现。
- 业务追踪继续按时间展示每笔供应商付款和每张采购收货单。

## 一致性与异常处理

付款和收货分别在事务内完成。数据库行锁与事务内重新汇总用于阻止并发超额付款和并发超量收货。非法采购单、未知采购明细、属于其他采购单的明细、负数、小数收货数量、全零收货、超额付款和超量收货均拒绝，且不产生部分流水或库存变化。

已有采购单通过现有付款流水和累计收货数量计算进度，无需人工迁移业务数据。数据库迁移仅移除付款唯一约束，并补充必要索引。

## 测试与验收

- 后端测试先覆盖首笔部分付款、第二笔付款、最终结清、超额付款和并发边界。
- 后端测试覆盖单产品与多产品分批收货、部分明细填零、最终收齐、全零拒绝、负数/小数拒绝、超量拒绝和事务回滚。
- 库存断言验证每次只将本次实收数量从在途转为实际库存，累计数量保持一致。
- 查询测试验证两条独立进度及总体完成条件。
- 前端测试验证两个操作入口可同时显示、付款结清后单独隐藏付款入口、收齐后单独隐藏收货入口，以及收货弹窗逐项校验。
- 运行相关后端测试、前端组件测试和前端生产构建，并通过实际接口验证多次付款与多次收货流程。
