# GMT 智能进销存管理系统

GMT 智能进销存管理系统提供客户、产品、订单、库存、采购和财务管理能力，支持 Excel 导入。

### 操作记录与整笔撤回

左侧“操作记录”统一查看操作内容、操作人员快照、时间、状态、来源地址、关联单据和模块，以及每条记录的变更前后值。支持按关键字、人员、模块、状态和日期筛选。新增、修改（含 PATCH）、删除、导入、复核、收付款、出入库及其自动采购联动都归入同一操作；只有实际改变业务数据的操作才保留记录；查看、查询、导出、登录、失败回滚及没有实际修改内容的保存不生成记录。仅更新时间或版本号不算业务修改。历史无变更记录不在列表展示，数据库原记录保留。菜单位于财务管理下方。

操作人可以撤回自己的操作，管理员可以撤回全部操作；权限由后端核验。撤回前先展示全部关联变更并填写原因，执行时再次校验依赖和当前数据。后续成功操作涉及同一业务实体时会列出阻挡记录，需从后往前处理；这种保护较保守，共用客户、产品等关联资料的后续操作也可能阻挡撤回。撤回在单个事务中按原写入顺序反向恢复，任何失败都会整体回滚。原记录标记“已撤回”，新的撤回记录保留人员、时间、原因及全部恢复明细；不支持再次撤回撤回记录。

新模块从 V66/V67 上线后开始保存完整快照。旧 operation_log 原始记录保留，无法补齐旧操作的快照，也不能撤回；无变更快照的记录不在操作记录列表展示。用户账号安全信息只记录脱敏元数据，不保存密码或令牌，不提供自动撤回。撤回影响系统数据，不会撤销现实中的物流、银行转账或已导出的文件。单据序号不会回退复用；恢复后的数据版本继续递增。产品图片删除时保留不可通过原图片接口访问的原文件，供撤回恢复；备份必须同时包含数据库与图片目录，文件清理需考虑操作记录保留周期。

实现使用 MySQL 行触发器记录所有业务表变更，连接上下文与业务事务同时提交/回滚。写入请求使用数据库互斥行串行化，避免多个服务实例同时写入与撤回。自动采购维护在原事务提交前执行；订单导入通过保存点保持单订单失败隔离，同时让成功项归入整批操作。日志持久化失败会阻止业务提交。V68/V69 补充真实变更识别和业务信息快照，每条变更保存相关订单号、客户订单号、采购/收发货/资金单号及客户、供应商、产品信息，并汇总修改字段。删除数据时仍保留原单据信息，后续改名不影响已保存的历史描述。

开发时新增业务表或修改字段，须通过新 Flyway 迁移同步更新 operation_audit_table 和对应触发器；不得修改已部署的 V66～V69。不要使用 TRUNCATE 或绕过 HTTP 事务直接写业务数据来实现用户功能。系统外的直接 SQL 维护不归属于用户操作，维护后可能导致历史操作不可撤回。数据库迁移账号需具备 TRIGGER 权限。

真实 MySQL 回归用例为 `OperationRecordMySqlTest`，只接受 `127.0.0.1:3306/gmt_audit_test_*` 的隔离测试库。设置 `OPERATION_AUDIT_MYSQL_URL` 与 `OPERATION_AUDIT_MYSQL_PASSWORD` 后，在 backend 运行 `mvn -pl app -am -Dtest=OperationRecordMySqlTest -Dsurefire.failIfNoSpecifiedTests=false test`；普通回归不连接该库。

### 订单支付与采购资金

订单管理和采购管理均显示已付金额、未付金额。订单支付默认填入当前全部未付金额，财务或管理员可修改为部分金额；每次支付从客户可用余额扣除，累计已付金额并更新剩余未付金额。金额必须大于零、不超过未付金额及客户余额，最多四位小数；旧窗口金额变化后须重新打开支付窗口。

资金管理的“采购付款”页签自动显示已复核的采购单，支持查询、付款登记、复核及付款记录查看。采购付款沿用原有登记和复核流程，审核通过后才计入已付金额，采购管理、资金管理、财务管理共用同一份付款记录。草稿采购单在复核后进入资金管理。

## Docker 部署

服务器需要安装 Docker Engine 与 Docker Compose Plugin。推荐 Linux 服务器使用 Ubuntu 22.04 或更高版本。

### 1. 上传项目并准备配置

将整个项目目录上传到服务器后，在项目根目录执行：

```bash
cp .env.example .env
nano .env
```

至少修改下面两项为不同的强密码：

```dotenv
MYSQL_PASSWORD=你的应用数据库强密码
MYSQL_ROOT_PASSWORD=你的数据库管理员强密码
```

若服务器的 `80` 端口已被其他网站使用，将 `APP_PORT=80` 改为例如 `APP_PORT=8080`。

### 2. 首次启动

```bash
docker compose up -d --build
```

首次构建会下载基础镜像并编译前后端，完成后访问：

```text
http://服务器IP
```

若设置了 `APP_PORT=8080`，则访问 `http://服务器IP:8080`。

系统健康检查地址：

```text
http://服务器IP/api/system/health
```

### 3. 常用运维命令

```bash
# 查看服务状态
docker compose ps

# 持续查看日志
docker compose logs -f

# 只查看后端日志
docker compose logs -f backend

# 停止服务（保留数据库与附件）
docker compose down

# 拉取新代码后更新
docker compose up -d --build
```

### 4. 备份与恢复

备份数据库：

```bash
mkdir -p backups
docker compose exec -T mysql sh -c 'mysqldump -uroot -p"$MYSQL_ROOT_PASSWORD" "$MYSQL_DATABASE"' > backups/gmt-$(date +%F).sql
```

恢复数据库前请先停止业务写入，然后执行：

```bash
cat backups/gmt-2026-08-06.sql | docker compose exec -T mysql sh -c 'mysql -uroot -p"$MYSQL_ROOT_PASSWORD" "$MYSQL_DATABASE"'
```

数据库数据保存在 Docker 卷 `gmt-inventory_mysql_data`，上传附件保存在 `gmt-inventory_attachment_data`。不要执行 `docker compose down -v`，否则这两个持久化卷会被删除。

## 服务结构

- `frontend`：Nginx 托管 Vue 前端，并代理 `/api` 请求。
- `backend`：Spring Boot 服务，启动时自动执行数据库迁移。
- `mysql`：MySQL 8 数据库，业务数据使用持久化卷保存。

默认仅开放前端 HTTP 端口；数据库和后端不会直接暴露到公网。

## 业务全景查看

在“订单管理”“采购管理”或“财务管理”的每一条记录右侧点击“查看”，可打开只读的业务全景：

- 订单可看到创建、客户收款、销售发票、库存锁定、订单发货出库及因缺货产生的关联采购单。
- 采购可看到创建、供应商付款、采购在途、到货入库以及它所补充的关联销售订单。
- 财务记录会自动打开对应的销售订单或采购订单全景；时间线中的关联单据也可继续点击查看。

库存、金额和状态均读取已办理的业务记录；“查看”不改变库存或单据状态。

## 供应商资料导入

供应商管理支持导入 `.xls` 和 `.xlsx` 文件。选择文件后应先查看预览结果：预览只解析、映射和校验文件，不会更新供应商主数据；确认行数、14 个字段的内容以及错误行为零后，再执行提交。

提交时可选择两种模式：

- `覆盖同名供应商（OVERWRITE）`：按规范化后的供应商名称更新同名记录并恢复启用状态，新增文件中的新供应商；文件中未出现的现有供应商保持原状态。
- `全量替换（REPLACE_ALL）`：同样更新同名记录并新增新供应商，同时将文件中未出现的现有供应商设为停用。该模式要求预览中没有错误行，适合以文件作为完整供应商清单的场景。

全量替换采用软停用，不会删除供应商记录，因此既有采购单、采购建议和产品供应商配置等历史外键仍然有效。停用的供应商不会作为当前可选供应商使用，但历史业务记录仍可追溯。

执行 `REPLACE_ALL` 前，建议先按上文“备份与恢复”章节备份数据库，并核对预览中的供应商数量、名称、税务登记号、开户地址和开户账户等文本字段。若文件不是完整清单，请使用 `OVERWRITE`，避免误停用文件外供应商。


## 已发货订单修改与收款调整

订单列表中的“修改”支持部分发货和全部发货的订单。订单原明细编号、发货批次、成本快照和关联采购记录会保留；价格、备注和订单数量可以调整。已发货明细不可删除或更换产品，数量不得低于已发货数量；已关联采购单的明细也不可删除或更换产品。正式订单保留原客户。

点击“确认保存”后，会再次弹出“确认已收金额”。可以保持原金额，管理员或财务也可以填写新的已收金额及必填调整原因。订单和金额调整在同一事务中保存，版本过期、余额不足或校验失败时一起回滚。

增加已收金额会扣减客户可用余额，减少已收金额会退回客户余额。系统新增收款差额和资金流水，不覆盖历史凭据；客户资金概览、月度净扣减、财务列表、订单详情、业务全景和财务导出均按已复核的确认金额统计。原发票保持原记录，可在发票管理中另行办理。

订单总额统一采用订单保存的 `total_amount`，财务列表及导出、订单支付、客户资金待收汇总和销售订单单据合计均与其一致。明细单价最多保留 8 位小数，汇总后四舍五入到分；V65 迁移扩大单价字段精度，不改写历史金额。历史单价已被舍入的订单，仅修改备注、联系方式或已收金额时保留原订单总额，修改产品、数量或单价后才重新计算；无法从历史两位小数单价还原已丢失的尾数。

增加订单数量后，系统只重新分配未发货部分的库存，并重新计算缺口和采购建议；无需再发货的订单维持“已发货”，仍有待发数量的订单按库存情况进入“等待发货”或“等待齐货”。


## 全状态采购单修改

采购管理中的实际采购单（手工和系统生成）在草稿、待付款、执行中、已收货及已完成状态均可打开完整的“修改采购”表单，修改明细、数量、采购报价、预计到货日期、交货地址和备注。多条明细可分别点击“修改明细”，同一单据仍使用同一供应商。

- 编辑默认保留原采购单价，历史产品或报价停用不妨碍保留原明细；主动选择有效报价才更新单价。新增或更换产品仍须有有效供应商报价。
- 已收货明细保留编号，不可删除或换产品，采购数量不得少于已收货量。有付款、收货或发票记录后不可更换供应商。原入库记录、成本历史、实际库存、付款和发票记录均保留。
- 草稿修改不计入在途；已复核采购按修改前后“采购数量减已收货数量”的差额调整在途，采购总额及付款/收货进度同步重算。已完成单据增加待收货量后重新进入执行流程。
- 系统采购保留原建议与销售关联的历史记录；削减采购会释放超出剩余供货量的缺口占用，并在独立事务中重算采购建议。修改失败时单据、明细和在途变动一起回滚。
- 已付金额统一按复核通过的确认金额统计。若修改后采购金额小于已确认付款，编辑页显示差额，保留实际付款，后续再处理差额，不自动伪造退款或改写发票。
- 编辑提交携带版本，旧页面遇到其他修改、收货或付款复核后须刷新，避免覆盖新数据。付款复核及发票登记与采购编辑使用同一采购单锁协调。


## 草稿采购单删除

采购管理中的实际采购单处于“草稿”时显示“删除”按钮。确认框列出采购单号；确认后采购单及全部明细在同一事务中删除，无法通过页面恢复。删除成功后刷新列表和总条数，删除末页最后一条记录时自动回到有效页。

删除只适用于尚未进入后续业务的独立草稿。后端锁定单据并核对状态和页面版本；已复核、已修改，或已有付款、发票、收货、库存流水、采购建议关联的单据均拒绝删除。采购建议继续使用原有复核/驳回流程。

草稿未计入在途，删除不调整实际库存、在途库存、资金或销售缺口，不重置采购单号序号，也不改动其他采购建议。采购列表、首页趋势及采购汇总导出从现有单据实时读取，删除后不再统计该单。采购汇总导出的草稿在途量为 0；财务导出与财务列表统一排除未复核采购草稿。
